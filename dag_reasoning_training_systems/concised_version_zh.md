# 技术分析：智能体推理训练系统的多层次DAG设计

## 执行摘要

本文综合了20篇关于基于DAG的训练系统的研究论文，通过4层框架分析架构：（1）数据即DAG，（2）训练/推理流水线，（3）编排状态机。核心洞察是**气泡在推理和训练引擎中表现不同**——**推理气泡是I/O密集型的**（等待外部工具），而**训练气泡是计算密集型的**（等待组同步的GPU）。理解这种区别能够针对每个阶段实施定向优化策略。

---

## 第一层：基础（数据即DAG）
![DAG_data](external/images/DAG_def.png)


**目标**：将推理编码为结构化依赖关系，而非线性序列。

训练数据不是扁平序列，而是从能力"超图"中提取的**子图**——其中超图代表所有可用的工具/智能体，任务仅激活相关的子集。

### 核心概念

**逻辑接近度**（DAG-Math）：不使用二元的通过/失败指标，而是衡量轨迹在DAG中遵循有效推导路径的程度。具有相似PASS@k分数的模型在逻辑接近度评估下可能具有显著不同的推理质量。

**步骤级价值**：SALT和AgentPRM等技术通过分析各个节点（步骤）对最终成功的贡献来分配信用：
- **SALT**：从多个rollout构建轨迹图；步骤质量 = f(success_rate, rarity, transition_patterns)
- **AgentPRM**：定义**Promise**（朝向目标的期望值）和**Progress**（动作的边际贡献）；使用GAE的TD估计实现8倍样本效率

**DAG质量维度**：
| 维度 | 指标 | 目的 |
|-----------|--------|---------|
| **结构有效性** | 逻辑接近度 | 轨迹是否遵循有效边？ |
| **节点质量** | Promise/Progress | 该步骤贡献多少？ |
| **边可靠性** | 转移成功率 | 该动作->状态转移是否有效？ |
| **图效率** | 可并行化分数 | 子任务能否并发执行？ |

### 数据层的DAG相关挑战

**挑战1：从超图中提取子图**
- **问题**：能力超图可能包含数千个潜在工具/智能体；为特定查询提取最优子图并非易事
- **解决方案**：
  - **GAP**：通过在标注的MHQA数据上进行SFT来学习预测任务图 → RL精炼
  - **TAMA/VITAL**：智能体在执行期间动态决定调用哪些工具
  - **训练数据**：人工标注的依赖图（昂贵但高质量）

**挑战2：DAG边上的多模态数据流**
- **问题**：DAG边必须携带异构数据类型——文本、图像、视频嵌入、结构化JSON
- **解决方案**：
  - **VerlTool**：统一工具API，具有模态声明；工具返回结构化输出
  - **TAMA**：返回多媒体的工具（图像、边界框）作为边数据流动
  - **VITAL**：视频的视觉工具箱——帧采样工具返回图像序列

**挑战3：跨DAG拓扑的信用分配**
- **问题**：当只能观察到最终结果而非中间步骤质量时，如何分配信用？
- **解决方案**：
  - **SALT**：轨迹图分析通过频率/成功率模式识别高质量步骤
  - **CRM**：多智能体协作奖励——专业评估器（事实性、有用性、安全性）+ 中心化聚合器
  - **优势塑形**：代理奖励优化揭示了困难样本上加权 = 奖励级正则化

**挑战4：动态vs静态DAG构建**
- **问题**：DAG应该预先计算（静态）还是在执行期间动态构建？
- **权衡**：
  - **静态DAG**：执行更快，预先计算的依赖关系；对新查询灵活性较低
  - **动态DAG**：适应查询复杂性；引入规划开销
- **当前状态**：GAP使用来自SFT的静态任务图；TAMA/VITAL使用动态工具选择

## 第二层：流水线（两个引擎）

### 阶段A：推理与Rollout引擎
![DAG-rollout](external/images/partial_rollout.png)


**约束**：外部工具延迟（I/O密集型）
**目标**：在智能体等待工具时最大化生成吞吐量。

**关键洞察**：推理气泡是**I/O密集型的**——由外部工具的延迟差异引起（例如，视频处理：10秒，代码解释器：0.1秒，网络搜索：2秒）。

#### 1. "推理气泡"问题

当智能体调用慢速工具时，如果GPU阻塞等待返回，它会空闲（气泡）。这与训练气泡根本不同：

| 气泡类型 | 推理（阶段A） | 训练（阶段B） |
|-------------|---------------------|-------------------|
| **根本原因** | 外部工具延迟（I/O等待） | 组调度同步（计算等待） |
| **持续时间** | 高度可变（0.1秒 - 10秒+） | 更可预测（毫秒级） |
| **依赖关系** | 独立于其他智能体 | 需要组中的所有GPU |
| **解决方案空间** | 异步执行、上下文切换 | 弹性回填、块打包 |

**解决方案**：异步部分Rollout（ROLL Flash）

系统使用**生产者-消费者模型**。当智能体遇到工具调用时：
1. 其状态（KV缓存）卸载到CPU（"冻结"）
2. GPU立即切换到来自全局队列的"填充任务"
3. 当工具结果返回时，重新加载原始状态并恢复

**架构**：
```
Rollout阶段（推理GPU）     训练阶段（训练GPU）
┌──────────────────┐             ┌──────────────────────────────────┐
│  LLMProxy        │──trajectories→│  AsyncController                 │
│  ├─ Worker 1     │             │  ├─ get_batch (from SampleBuffer)│
│  ├─ Worker 2     │             │  ├─ train_step                   │
│  └─ Worker N     │             │  └─ model_update (broadcast)     │
└────────┬─────────┘             └──────────────────────────────────┘
         │
         ▼
┌──────────────────┐
│  EnvManager 1-N  │──tool_results──┐
│  └─ BaseEnv      │               │
│  └─ Event Loop   │               │
└──────────────────┘               │
                                   │
                           ┌───────┴────────┐
                           │ SampleBuffer   │
                           │ (freshness     │
                           │  constraint α) │
                           └────────────────┘
```

**结果**：
- **环境级异步**：1.23× - 1.58×加速（SWE-bench、ALFWorld）
- **队列调度**：比同步批处理快2.16×
- **Rollout-训练解耦**：128 GPU上2.24×吞吐量

#### 2. DAG感知调度：依赖并行执行

**问题**：传统ReAct顺序处理工具调用，即使独立子任务可以并行执行。

**解决方案**（GAP）：构建**依赖感知任务图**，其中：
- 节点 = 带工具注释的子任务
- 边 = 数据依赖关系（A的输出作为B的输入）
- 调度器并行启动所有就绪节点（无待处理依赖）

**示例DAG**：
```
问题："比较法国、德国和意大利的GDP和人口"

[搜索：法国GDP] ─┐
[搜索：德国GDP]─┼──→ [比较GDP] ─┐
[搜索：意大利GDP] ─┘                    └──→ [最终答案]
                                              ┌─────────────────────┘
[搜索：法国人口] ─┐                     │
[搜索：德国人口]─┼──→ [比较人口] ────┘
[搜索：意大利人口] ─┘
```

**并行执行**：搜索任务同时执行（1.74×加速）；比较任务顺序执行（需要依赖）。

**性能**：
| 问题类型 | 独立子任务 | 并行加速 |
|---------------|----------------------|------------------|
| 简单查找 | 1-2 | 1.2× |
| 多跳（3个实体） | 3 | 1.8× |
| 多跳（5+个实体） | 5+ | 2.3× |

#### 3. Rollout内并行的提示复制

**问题**：多候选解码（num_return_sequences >> 1）强制单个worker顺序解码所有响应。

**解决方案**（ROLL Flash）：将每个提示扩展为**n个独立的rollout任务**：
```
传统：提示A → Worker 1 → [A1, A2, ..., A16]（顺序瓶颈）

提示复制：
提示A1 → Worker 1 → A1
提示A2 → Worker 2 → A2
...
提示A16 → Worker 16 → A16
```

**性能**：根据批配置实现1.30-1.95×加速。

#### 4. 冗余环境Rollout（弹性）

**问题**：环境不稳定（fail-slow、fail-stop）造成瓶颈。

**解决方案**（ROLL Flash）：两个可调控制：
- **num_env_groups**：更多并发环境组
- **group_size**：每组更多候选轨迹

**关键发现**：增加num_env_groups比增加group_size更有效（5.40× vs 5.28×加速）。

### 阶段B：训练引擎

![DAG-chunk](external/images/chunk-node-flow.png)

**约束**：同步屏障（计算密集型）
**目标**：在不规则训练数据上最大化MFU（模型FLOPS利用率）。

**关键洞察**：训练气泡是**计算密集型的**——由不规则序列和分布式训练所需的同步屏障（环形注意力、组调度）引起。

#### 1. "训练气泡"问题

训练需要**组调度**：多个GPU必须同时处理相同的序列块以计算注意力。如果一个GPU提前完成，它必须等待其他GPU（气泡）。

**这与推理气泡不同**：
| 方面 | 推理气泡 | 训练气泡 |
|--------|-----------------|-----------------|
| **等待的资源** | 外部I/O（工具响应） | 其他GPU（同步） |
| **可预测性** | 高度可变（0.1秒 - 10秒+） | 更可预测（毫秒级） |
| **缓解措施** | 切换到另一个智能体的工作 | 用独立块填充 |
| **状态管理** | 将上下文卸载到CPU | 将激活保留在VRAM中 |

**解决方案**：弹性回填（AnchorTP / 弹性调度器）

调度器检测组调度中的空闲间隙，并插入小的独立块（来自其他样本）来填充气泡。

**机制**：
```
无气泡填充的时间线：
GPU 0：[Chunk1组调度] [空闲等待...] [Chunk1组调度]
GPU 1：[Chunk1组调度] [空闲等待...] [Chunk1组调度]
GPU 2：[Chunk1组调度] [空闲等待...] [Chunk1组调度]
GPU 3：[Chunk1组调度] [空闲等待...] [Chunk1组调度]

有气泡填充的时间线：
GPU 0：[Chunk1组调度] [小块A] [Chunk1组调度]
GPU 1：[Chunk1组调度] [小块B] [Chunk1组调度]
GPU 2：[Chunk1组调度] [小块C] [Chunk1组调度]
GPU 3：[Chunk1组调度] [小块D] [Chunk1组调度]
```

#### 2. DAG感知块调度：统一分块（ChunkFlow）

**问题**：可变长度智能体轨迹（4k - 32k令牌）导致巨大的负载不平衡和流水线气泡。

**解决方案**（ChunkFlow）：将所有数据切成**统一块**（例如，4096个令牌），同时保留逻辑DAG依赖关系。

**块构建算法**：
1. **长序列**（> ChunkSize）：分成多个统一块
2. **短序列**（< ChunkSize）：装箱在一起以填充一个块
3. **依赖块**（来自分割序列）：通过DAG边维护因果顺序

**状态感知调度**：
- **独立块**：独立处理，无状态共享
- **依赖块**：通过StateStore共享KV缓存；按因果顺序执行（前向：1→2→3，后向：3→2→1）

**性能**：比Megatron-LM基线快**4.53×**；内存随K×ChunkSize缩放，而不是最大序列长度。

**流水线气泡减少**：
| 方法 | 气泡比例 | 改进 |
|--------|--------------|-------------|
| 标准1F1B（可变） | 57.14% | — |
| 状态感知1F1B（K=1） | 54.1% | 提高8% |
| 状态感知1F1B（K=2） | 47.8% | 提高12% |

#### 3. 弹性与恢复（AnchorTP）

**问题**：如果特定块导致失败（OOM或挂起），传统系统会终止整个训练作业。

**解决方案**（AnchorTP）：**弹性张量并行**——将失败的分片迁移到不同的物理GPU而不终止作业。

**故障恢复**：
| 故障类型 | 传统方法 | AnchorTP方法 |
|--------------|----------------------|-------------------|
| OOM | 终止作业，从检查点重启 | 将分片迁移到更大的GPU |
| 挂起/掉队者 | 无限期等待或超时 | 将分片迁移到更快的GPU |
| 网络分区 | 作业失败 | 使用可用分片继续 |

#### 4. DAG级信用分配

**问题**：当节点具有复杂依赖关系且只能观察到最终结果时，如何分配信用？

**解决方案**：
- **SALT**：轨迹图分析——步骤质量 = f(success_rate(state), success_rate(state,action), rarity(state))
- **AgentPRM**：Promise（期望值）+ Progress（边际贡献）；TD自举消除了人工标注的需求
- **CRM**：多智能体协作奖励——专业评估器 + 中心化聚合器；45%奖励方差减少

**性能**：
| 技术 | 样本效率 | 收益 |
|------------|-------------------|------|
| SALT | 训练步骤减少25-34% | 绝对精度提高3-5% |
| AgentPRM | 样本减少8倍 | 与人工标注的PRM相当 |
| CRM | 方差减少45% | rewardBench提高7-9% |

### 按阶段比较：气泡与调度

| 特性 | 阶段A：推理（Rollout） | 阶段B：训练 |
|---------|------------------------------|------------------|
| **主要瓶颈** | 外部工具延迟（I/O密集型） | 计算/同步屏障（计算密集型） |
| **"气泡"原因** | 等待环境/工具响应 | 等待其他GPU（组调度） |
| **气泡持续时间** | 高度可变（0.1秒 - 10秒+） | 可预测（毫秒级） |
| **调度单元** | 样本/提示（队列调度） | 块/张量（组调度） |
| **状态管理** | 冻结上下文（卸载到CPU） | 活跃VRAM（上下文并行） |
| **关键算法** | ROLL Flash（异步生产者-消费者） | AnchorTP（弹性张量并行） |
| **并行驱动因素** | 工具独立性（GAP任务图） | 组调度约束（ChunkFlow） |
| **主要论文** | ROLL Flash (arXiv:2510.11345) | ChunkFlow (arXiv:2503.02356) |
| **实现加速** | 2.24×（128 GPU） | 4.53×（7B，256K上下文） |

## 第三层：编排（状态机）

![DAG-state](external/images/overall_system.png)

**目标**：管理阶段A（推理）和阶段B（训练）之间的生命周期流。

### 节点生命周期状态机

宏观调度器将整个系统视为**DAG节点生命周期状态机**：

```
     ┌─────────┐     tool_call      ┌──────────┐
     │         │ ──────────────────>│          │
     │ 推理     │  (发送到环境)      │ 待处理    │
     │ (红色)   │                   │ (蓝色)   │
     │         │ <──────────────────│          │
     └────┬────┘    结果返回        └─────┬────┘
          │                              │
          │                              │
          │    ┌─────────────────────────┴────────┐
          │    │                                  │
          │    ▼                                  ▼
          │ ┌──────────┐                    ┌──────────┐
          │ │ 精炼     │                    │ 训练     │
          │ │ (绿色)  │                    │ (黄色)  │
          │ │          │◀────────────────────│          │
          │ └─────┬────┘     梯度           └──────────┘
          │       │
          └───────┴─────────────────────┐
                                ▼
                          ┌──────────────┐
                          │ 已完成       │
                          └──────────────┘

路径① (RL)：待处理 → 训练
路径② (SFT)：待处理 → 精炼 → 训练
```

### 状态转换与DAG含义

| 转换 | 触发条件 | DAG含义 |
|------------|---------|-----------------|
| 推理 → 待处理 | 需要工具调用 | DAG节点被外部依赖阻塞 |
| 待处理 → 推理 | 工具结果返回 | DAG节点解除阻塞；继续执行 |
| 待处理 → 精炼 | 节点被选中进行SFT | DAG轨迹被修改（oracle注入） |
| 待处理 → 训练 | 节点有奖励 | DAG边由奖励信号加权 |
| 精炼 → 训练 | 节点被纠正 | DAG节点成为训练样本 |

### 集成挑战：异步 vs 新鲜度

**问题**：推理引擎（阶段A）使用策略π生成数据。训练引擎（阶段B）将策略π更新为π'。如果推理超前太多，它会从旧策略生成陈旧数据。

**解决方案**（AReaL、ROLL Flash）：**异步比率**限制策略版本差距。

**异步比率公式**：
| 系统 | 参数 | 定义 | 最优值 |
|---------|-----------|------------|---------------|
| **ROLL Flash** | α | 当前策略版本n - 样本启动版本 ≥ (n-α) | 2（对模型大小不敏感） |
| **AReaL** | β | 推理可以比训练领先β个版本 | 2-4（取决于批大小） |

**权衡**：
| 值 | 优点 | 缺点 |
|-------|------|------|
| α=1（同步） | 最大新鲜度 | 生成阻碍训练 |
| α=2（推荐） | 接近最大吞吐量，最小陈旧度 | 小的离策略惩罚 |
| α=4+ | 最大吞吐量 | 显著的离策略退化 |

**训练稳定性**：离策略算法（GRPO、解耦PPO、TOPR）有效补偿陈旧度——异步在达到2.24×吞吐量的同时实现与同步相当的精度。

### DAG相关编排挑战

**挑战1：多智能体DAG协调**
- **问题**：多个智能体同时执行不同的DAG分支；如何协调它们的进度？
- **解决方案**（VerlTool）：统一工具API，具有标准化的模态声明；调度器统一处理不同的工具
- **结果**：跨6个域的并行工具执行实现近2×加速

**挑战2：通过DAG传播奖励**
- **问题**：最终奖励必须通过DAG边向后传播以归功于所有贡献节点
- **解决方案**：
  - **AgentPRM**：Promise/Progress指标与TD估计——信号通过轨迹DAG向后流动
  - **CRM**：并行评估器馈送聚合器——多视角奖励捕获DAG结构
  - **SALT**：轨迹图构建——步骤质量从图位置和结果相关性得出

**挑战3：动态DAG拓扑适应**
- **问题**：DAG结构因查询复杂性而异；简单查询产生浅层DAG，复杂查询产生更深的DAG
- **解决方案**（GAP）：两阶段训练——在静态图演示上进行SFT → RL精炼以实现动态构建
- **开放问题**：模型能否学习在没有人工标注的情况下预测最优DAG拓扑？

## 核心要点

### 1. 气泡根本不同

| 方面 | 推理气泡 | 训练气泡 |
|--------|-------------------|------------------|
| **本质** | I/O密集型（外部工具） | 计算密集型（GPU同步） |
| **持续时间** | 高度可变（100×方差） | 可预测（均匀尺度） |
| **解决方案** | 异步执行、上下文切换 | 弹性回填、块打包 |

### 2. 异步需要新鲜度管理

- **小异步比率足够**：α=2在最小离策略退化下实现接近最大吞吐量
- **离策略算法补偿**：GRPO、解耦PPO、TOPR有效处理陈旧度
- **资源分配**：70% GPU用于rollout（瓶颈），20%用于训练，10%用于精炼

### 3. DAG结构实现优化

- **依赖感知规划**（GAP）：通过并行独立子任务实现1.74×加速
- **轨迹图分析**（SALT）：25-34%样本效率提升
- **多智能体奖励**（CRM）：通过专业评估器实现45%方差减少

### 4. 统一分块具有变革性

- **内存可预测性**：随K×ChunkSize缩放，而不是最大序列长度
- **流水线效率**：通过状态感知1F1B减少12%气泡
- **负载均衡**：长上下文微调4.53×加速

### 5. 工具集成需要标准化

- **统一API**（VerlTool）：异步能力 + 模态声明实现并行执行
- **多媒体支持**：工具返回图像/视频/文本——DAG边携带异构数据
- **近2×加速**：跨6个域的并行工具执行

1. **自适应DAG构建**：模型能否在没有专家标注的情况下学习预测最优子图？
2. **跨层信用分配**：如何设计考虑DAG位置、步骤质量、结果的统一奖励函数？
3. **分层DAG**：我们能否组成多层DAG，其中高层规划触发子智能体DAG？
4. **DAG重用**：哪些子轨迹应该被缓存为可重用模式？
5. **多智能体DAG协调**：如何协调探索不同DAG分支的多个智能体？
